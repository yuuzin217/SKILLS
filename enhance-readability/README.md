# enhance-readability

コードの可読性とドキュメントを改善するスキルです。動作と外部仕様は原則として維持します。

## 概要

命名、構造、コメント、ドキュメントを改善し、コードを読む人が責務・意図・制約・副作用を正確に理解できる状態を目指します。

コメントを増やすこと自体は目的ではありません。確認できる根拠がある場合にのみ設計意図を記述し、自明な説明や推測は避けます。

## いつ使うか

- 命名や制御フローを明確にしたい
- 関数の分割や不要な複雑さの整理を依頼したい
- GoDoc / JSDoc / TSDoc など言語に適した API ドキュメントを追加したい
- 可読性向上のためのリファクタリングを依頼したい
- コードレビュー観点で可読性の問題点を整理してほしい

## 使わない場面

- 機能追加や仕様変更が主目的のとき
- パフォーマンス最適化が主目的のとき
- 大規模なアーキテクチャ再設計が主目的のとき

## 使い方

### 1. スキルの有効化

Cursor のスキル設定で `enhance-readability/` ディレクトリをスキルとして登録します。

### 2. プロンプト例

```
/enhance-readability
このサービス層の可読性を改善して。動作は変えないで。
```

```
この関数の命名と制御フローを整理して、必要なら GoDoc も追加して。
```

```
この React コンポーネントの可読性をレビューして。コードは変更しないで。
```

```
公開 API の JSDoc を追加して。型情報と重複する説明は不要。
```

### 3. エージェントの方針

1. **動作を維持する** — 公開 API、副作用、エラー条件、並行処理の挙動は変更しない
2. **根拠のある説明だけを書く** — コード、テスト、Issue、ドキュメントなどから確認できる場合にのみ設計意図を記述する
3. **自明なコメントを避ける** — コードを自然言語に置き換えただけのコメントは追加しない
4. **コードで表現できることはコードで表現する** — 命名改善、早期 return、定数化、責務分割を優先する
5. **リポジトリ規約を優先する** — 周辺コード、lint、formatter、既存ドキュメント形式に合わせる
6. **言語別の標準に従う** — Go は GoDoc、TypeScript / JavaScript は JSDoc / TSDoc、React は非自明な責務や副作用のみ説明する
7. **TODO / FIXME は慎重に扱う** — 原則として報告のみとし、Issue 番号や対応方針がある場合に限って追加する

## 作業結果に含まれる内容

- 改善した箇所の概要
- 命名・コメント・リファクタリングの理由
- 動作変更の有無
- 確認できなかった設計意図
- 実行した formatter / lint / 型チェック / テスト
- 残っている懸念事項
