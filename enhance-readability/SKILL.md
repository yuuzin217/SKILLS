# コードの可読性向上

## 目的

コードの動作と外部仕様を原則として維持しながら、命名、構造、コメント、ドキュメントを改善します。

コメントを増やすこと自体を目的にせず、コードを読む人が次の情報を正確に理解できる状態を目指してください。

- コードの責務
- 実装上の意図
- 重要な制約
- 非自明な前提
- 副作用やエラー条件
- 採用した実装のトレードオフ

## 基本原則

### 1. 根拠のない設計意図を作らない

「なぜこの実装になっているか」は、次のいずれかから確認できる場合にのみ記述してください。

- ユーザーから提供された説明
- コードから明確に確認できる制約
- テストコード
- Issue
- 設計書
- ADR
- リポジトリ内のドキュメント
- 使用している外部APIやライブラリの公式仕様

理由を確認できない場合は、推測をコメントとして書かないでください。

設計意図が不明な場合は、事実として補完せず、確認できなかった事項として作業結果に記載してください。

### 2. 自明なコメントを追加しない

コードをそのまま自然言語に置き換えただけのコメントは、原則として追加しないでください。

次のようなコメントは避けてください。

```go
// IDが空か確認する
if data.ID == "" {
	// UUIDを生成する
	data.ID = uuid.NewString()
}
```

コメントでは、主に次のような非自明な情報を説明してください。

- 実装上の制約や不変条件
- 一見すると不要に見える処理が必要な理由
- 外部システムや互換性による制約
- 副作用
- 所有権
- 並行処理上の注意
- 処理順序への依存
- 採用した方法のトレードオフ
- 特殊なエラー条件や境界条件

古くなったコメント、コードと矛盾するコメント、コードと内容が重複するコメントは削除または修正してください。

### 3. コードで表現できることはコードで表現する

コメントで処理を補足する前に、次の方法でコード自体を明確にできないか検討してください。

- 変数名の改善
- 関数名の改善
- 型名の改善
- 複雑な条件式の分割
- 早期returnの利用
- 意味のある値の定数化
- 関数の責務分割
- 型による制約の表現
- 重複処理の整理
- 不要な抽象化の削除

コメントは、不明瞭なコードを正当化するために使用しないでください。

### 4. リポジトリの既存規約を優先する

変更前に、可能な範囲で次の情報を確認してください。

- 周辺コード
- 公開API
- 呼び出し元
- テストコード
- `README`
- `CONTRIBUTING`
- コーディング規約
- formatter設定
- lint設定
- 型チェック設定
- 既存のコメントやドキュメント形式

リポジトリ固有の規約がある場合は、その規約を優先してください。

固有の規約が確認できない場合は、対象言語の標準的な慣習に従ってください。

## 言語別のドキュメント方針

### Go

- exportedな型、関数、メソッド、定数、変数には、必要に応じてGoDocを追加する
- GoDocは対象の識別子名から始める
- 利用者に必要な場合は、エラー条件、副作用、並行処理上の制約を記述する
- 自明な非公開関数にドキュメントコメントを強制しない
- 関数内の処理を一行ずつ説明するコメントは追加しない

例：

```go
// Save assigns an identifier when necessary and persists data.
func (s *Service) Save(ctx context.Context, data *Data) error {
	if data.ID == "" {
		data.ID = uuid.NewString()
	}

	return s.repo.Store(ctx, data)
}
```

### TypeScript / JavaScript

- 公開APIや複数箇所から利用される関数には、必要に応じてTSDocまたはJSDocを使用する
- 型情報と重複する引数や戻り値の説明は避ける
- エラー条件、副作用、利用上の制約がある場合は明記する
- 非公開かつ自明な関数にJSDocを強制しない

例：

```ts
/**
 * Persists a user after normalizing its externally supplied identifier.
 *
 * @throws When the repository cannot persist the user.
 */
async function saveUser(user: User): Promise<void> {
  await repository.save(normalizeUser(user));
}
```

### React

Reactコンポーネントには、次のような非自明な情報がある場合のみ説明を追加してください。

- コンポーネントの責務
- 複雑な状態遷移
- 副作用
- 外部データとの同期
- 再レンダリング上の制約
- アクセシビリティ上の考慮
- 通常とは異なる設計を採用した理由

JSXの表示内容をそのまま説明するコメントは追加しないでください。

## リファクタリング方針

可読性向上のため、必要に応じて次の変更を行ってください。

- 不明瞭な命名の改善
- 複雑な条件式の単純化
- ネストの削減
- 早期returnへの変更
- マジックナンバーや文字列の定数化
- 複数の責務を持つ関数の分割
- 重複処理の整理
- 不要な分岐の削除
- 不要な抽象化の削除
- 型を利用した意図の明確化

ただし、単に関数が長いという理由だけで分割しないでください。

分割後の関数名が処理内容を明確に表現できず、処理の流れが追いにくくなる場合は、分割しない方が適切な可能性があります。

1か所でしか使用されない単純な処理を、無理に共通関数や抽象レイヤーへ切り出さないでください。

## 動作の維持

明示的な依頼がない限り、次の要素を変更しないでください。

- 外部から観測可能な動作
- 公開API
- 関数やメソッドのシグネチャ
- データ形式
- エラーの種類
- エラーの発生条件
- 副作用
- 副作用の実行順序
- トランザクション境界
- 並行処理の挙動
- 永続化のタイミング
- パフォーマンス特性に重大な影響を与える処理

可読性向上の範囲を超える変更が必要だと判断した場合は、直接混在させず、別の改善提案として報告してください。

## TODOとFIXMEの扱い

境界条件、潜在的な不具合、パフォーマンス上の懸念を発見しても、原則としてコードへ自動的に`TODO`や`FIXME`を追加しないでください。

まず、レビュー結果または残存課題として報告してください。

コードへコメントを追加するのは、次のいずれかに該当する場合に限定してください。

- ユーザーが明示的に追加を求めている
- 対応するIssue番号が存在する
- 具体的な対応方針が決まっている
- 一時的な制約であることが明確である

追加する場合は、可能であれば対応理由やIssue番号を含めてください。

```ts
// TODO(#123): Remove this fallback after the legacy API is retired.
```

期限、理由、対応方針のない曖昧な`TODO`は追加しないでください。

## 作業手順

1. 対象コードと周辺コードを確認する
2. 公開API、呼び出し元、テスト、リポジトリ規約を確認する
3. 可読性を妨げている要因を特定する
4. 動作を維持したまま、必要最小限の変更を行う
5. 不要なコメントを削除する
6. 必要なドキュメントだけを追加する
7. formatter、lint、型チェック、テストを可能な範囲で実行する
8. 変更内容と未確認事項を報告する

## 依頼内容ごとの対応

### レビューのみを依頼された場合

コードを直接変更せず、次の内容を提示してください。

- 問題箇所
- 問題である理由
- 改善案
- 改善の優先度
- 動作変更の可能性
- 確認が必要な設計意図

### 編集を依頼された場合

許可された範囲でコードを変更してください。

変更後は、formatter、lint、型チェック、テストを可能な範囲で実行してください。

### 対象範囲が明示されている場合

指定されたファイルや関数の範囲を超えて、大規模なリファクタリングを行わないでください。

範囲外にも問題を発見した場合は、変更せずに別途報告してください。

## 出力内容

作業結果には、必要に応じて次の内容を含めてください。

- 改善した箇所の概要
- 命名を変更した理由
- コメントを追加した理由
- コメントを修正または削除した理由
- 実施したリファクタリング
- 動作変更の有無
- 確認できなかった設計意図
- 実行したformatter
- 実行したlint
- 実行した型チェック
- 実行したテスト
- 実行できなかった検証
- 残っている懸念事項

変更が不要な場合は、不要なコメントや抽象化を追加せず、変更不要である理由を説明してください。

## 禁止事項

次の行為を行わないでください。

- コードから確認できない設計意図を事実として書く
- コメント数を増やすこと自体を目的にする
- コードを自然言語へ置き換えただけのコメントを追加する
- 動作変更を可読性改善として隠す
- 公開APIを無断で変更する
- 不要な抽象化を追加する
- 根拠のない`TODO`や`FIXME`を追加する
- テストが通ったと未確認のまま断言する
- 実行していないformatter、lint、型チェック、テストを実行済みと報告する

## 例

### 入力

```go
func (s *Service) Save(ctx context.Context, data *Data) error {
	if data.ID == "" {
		data.ID = uuid.NewString()
	}

	return s.repo.Store(ctx, data)
}
```

### 改善後

```go
// Save assigns an identifier when necessary and persists data.
func (s *Service) Save(ctx context.Context, data *Data) error {
	if data.ID == "" {
		data.ID = uuid.NewString()
	}

	return s.repo.Store(ctx, data)
}
```

### 作業結果

- exportedメソッドであるため、GoDocを追加しました
- 処理をそのまま説明する関数内コメントは追加していません
- IDをサービス層で生成する設計上の理由は、提示されたコードからは確認できません
- 通知処理やドメインイベントの都合など、確認できない理由はコメントへ追加していません
- メソッドの挙動と公開シグネチャは変更していません
