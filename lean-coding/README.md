# lean-coding

「最少のコードで動くもの」を書かせるための、AI コーディングエージェント向け行動規則スキルです。

## 概要

Marcos Hernanz（@MarcosHernanz、当時 Vercel の Next.js チームの Software Engineer Intern）が「~60B tokens 回して辿り着いた自分の AGENTS.md 全文」として 2026-08-02 に X へ投稿した 7 条を、使う手順つきのスキルに整形したものです。

中核は「一番単純な実装を選ぶ／既存依存と成熟したライブラリを先に使う／車輪の再発明をしない」。
ただし優先順位は **正しさ・安全性・データ保全 ＞ 要件上の互換性 ＞ コード量の少なさ** で、簡潔さのためにバリデーションやテストを落とす使い方はしません。
エージェントが書きがちな「余分なコード」を、書く前・書く途中・diff 監査の 3 点で止めます。

## いつ使うか

- side project、内部ツール、プロトタイプの実装・バグ修正
- エージェントが書いたコードのレビュー（抽象化や依存追加が過剰でないかの監査）
- AGENTS.md に入れる前の、規則の運用テスト

## 注意（本番ガードレール）

- 対象が本番かどうか**判定できない場合は本番として扱います**
- ルール 1「後方互換を残すな」は**コード経路だけ**に適用し、保存済みデータ・DB・マイグレーション・旧データ形式を読むコードには決して適用しません（拡散要約経由の伝聞として、本番 DB のテーブルを落としかけたという警告が伝えられています）
- 本番コードでは、公開 API など互換が要る相手がある場合は互換維持を優先します
- 「~60B tokens」は著者の自己申告で、第三者検証はありません

## 使い方

### 1. スキルの有効化

`lean-coding/` ディレクトリをスキルとして登録します（このリポジトリの他のスキルと同じ方法）。

### 2. プロンプト例

```
この機能を lean-coding で実装して。既存依存で済むなら新しいパッケージは足さないで。
```

```
この diff を lean-coding の監査チェックリストで見て、余分な抽象化や互換レイヤを指摘して。
```

```
このリポジトリは本番扱いで進めて。データとマイグレーションには触らないで。
```

### 3. エージェントの手順

1. **書く前に** — 本番判定（不明なら本番扱い）をし、既存コード・既存依存を調べる
2. **書きながら** — 「将来のため」の抽象・設定・フォールバックを足さない
3. **書いた後に** — テスト・lint・型チェックを実行し、diff 監査チェックリストで余分とデータ側への影響を潰す
