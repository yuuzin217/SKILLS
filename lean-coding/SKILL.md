name: lean-coding
description: Write or review code with the least code that actually works — no speculative abstraction and no reinventing what the project or an established library already provides. Use when implementing a feature or fixing a bug in a side project, internal tool, or prototype, or when auditing agent-written code for excess. Do not use when compatibility itself is the requirement, when the task's premise is preserving observable behavior (use enhance-readability), or for production data, schema, or migration work.

# lean-coding — 最少のコードで動くものを書く

AI コーディングエージェントが「新人のように何でも自作しようとする」振る舞いを止めさせるための行動規則。
出典は Marcos Hernanz（@MarcosHernanz、当時 Vercel の Next.js チームの Software Engineer Intern）が
2026-08-02 に X へ投稿した「After doing ~60B tokens, this is my full AGENTS.md」。
原典は 7 条で、詳細と出典の注意は末尾の「出典と注意」に置く。

## 優先順位（これが全規則に勝つ）

判断が割れたら、この順序で決める。下位は上位を決して覆さない。

1. **正しさ・安全性・データ保全** — バリデーション、エラーハンドリング、セキュリティ、
   テストは「余分なコード」ではない。簡潔さのために落とさない。
2. **要件上の互換性** — 互換維持が要件・利用者・連携先から求められるなら、互換を残す。
3. **コード量の少なさ** — 上の 2 つが同等に満たされる場合に限り、「迷ったら減る方」を選ぶ。

## コアルール（原典 7 条）

1. **後方互換を残すな（コード経路のみ）**
   廃れたコード経路は、互換レイヤ・フォールバックを足して延命せず、削除する。
   ただし「コード経路」に次は含めない（＝データ側として扱い、本スキルでは触らない）：
   保存済みデータ、DB スキーマとマイグレーション、**データ形式を読む／書くコード**、
   スキーマを定義するコード、ユーザーのファイル。これらは「本番ガードレール」に従う。

2. **現在の要件を満たす一番単純な実装を選べ**
   予防的な抽象化をしない。「将来使うかも」という設定層・オプション・汎用化を足さない（YAGNI）。
   ルール 4 との線引き：責務が実際に分かれているなら分割する。今は存在しない
   将来の責務のために分割・汎用化するなら、それは予防的抽象化。

3. **システムは層で育てろ**
   まず最小の end-to-end で動く版を通し、動いてから上に足す。
   将来の複雑さへの備えを理由に、今動いているものを壊して作り替えない。
   ルール 7 との切り分け：**アーキテクチャの境界と判断は最初から長期で決める（ルール 7）、
   機能の実装量は最小から始める（ルール 3）。** 最小版とは「境界は本物、機能は最小」のことであり、
   境界ごと仮にする「まず仮で」とは違う。

4. **コンポーネントはモジュールに、関心は分離**
   1 つの部品に 1 つの責務。境界を越えた密結合を作らない。

5. **成熟したライブラリを優先せよ**
   実績があり保守されている第三者ライブラリがあるなら、自前で書き直さない。
   ただし依存の追加自体にもコスト（バンドル、lockfile、保守対象）がある。
   目安：十数行で済み保守も軽い処理なら標準ライブラリ／自前を、複雑で壊れやすい処理
   （日付・時刻、暗号、パース等）は行数が少なくても成熟ライブラリを優先する。

6. **既存の依存を先に調べよ**
   新しいパッケージを足す／自作する前に、プロジェクトが既に入れている依存でできないか確認する。
   調査の停止条件は「手順（書く前に）」に置く。無制限に調べない。

7. **アーキテクチャ判断は長期で、一時しのぎをしない**
   「まず仮で、あとで直す」を受け入れない。仮実装はほぼ必ず残る前提で判断する。
   ルール 1 との裁定：互換を切るかどうかは、影響範囲（利用者・データ・連携先）を
   確認した上で長期の視点で決める。影響範囲が未確認なら切らない。

### 補足の 1 条（原典には無い）

拡散した要約（@AYi_AInotes、2026-08-04）が足した 8 条目として広まっているもの。
原典の規則ではないが、ルール 5・6 と同方向なので補助として使う：

8. **成熟した製品が同じ問題をどう解いているか先に見よ**
   実証済みのパターンを借り、ゼロから発明しない。
   これは新規設計のときだけの任意調査であり、小さい修正では行わない（手順参照）。

## 手順

### 書く前に

1. **本番判定をする。** 対象リポジトリが本番か判定する：実利用者がいるか、実データを持つか、
   本番への接続情報（`.env`、接続文字列等）を含むか。
   **判定できない場合は本番として扱う（fail-closed）。** 判定結果と根拠を作業報告に残す。
2. 対象プロジェクトの既存コード・既存依存を調べる（ルール 6）。
   調べる範囲は原則として、依存一覧（package.json / lockfile 等）と既存ユーティリティまで。
   個別ライブラリのドキュメントと型まで掘るのは「既存依存でできそう」と当たりが付いたときだけ。
   ここで打ち切ってよい。
3. 新規設計の場合に限り、成熟したライブラリ／製品の解き方を確認する（ルール 5・補足 8）。
   小さいバグ修正・小さい変更ではこの調査は行わない。検索できない環境ではスキップしてよい。

### 書きながら

- 新しい抽象・設定・フォールバックを足したくなったら、その場で「現在の要件に必要か？」と問う。答えが「将来のため」なら足さない（ルール 2）。
- 既存経路を置き換える場合、旧経路は残さず消す（ルール 1）。ただしデータ側（ルール 1 の除外リスト）に触れる場合は止まって「本番ガードレール」に従う。

### 書いた後に（検証＋ diff 監査）

1. **検証を実行する。** 既存のテスト、lint、型チェックを実行し、結果を報告する。
   互換経路を削除した場合は、それをカバーしていたテストがどうなったか（削除したのか、
   失敗していないか）を特に確認する。検証していないものを「動く」と報告しない。
2. **diff 監査**をする。当てはまったら原則として差し戻して単純化する。
   残す場合は、理由を作業報告（PR がある場合は PR 本文）に明記する。

   - [ ] 互換レイヤ／フォールバック／「念のため」の分岐が増えていないか
   - [ ] 現在の要件を超える抽象化・設定項目が増えていないか
   - [ ] 既存依存や標準ライブラリで済むものの再実装が増えていないか
   - [ ] 新規パッケージは、既存依存で代替できないことを確認した上か（確認した内容を報告に書けるか）
   - [ ] 動いていたコードを、未完成の複雑なものに置き換えていないか
   - [ ] 一時しのぎの実装が「あとで直す」前提で残っていないか
   - [ ] **データ側を消していないか**：保存済みデータ、マイグレーション、旧データ形式を
     読む／書くコード、スキーマ定義を削除・変更していないか。している場合は本スキルの
     適用範囲外として、人の判断なしに進めていないか

## 本番ガードレール

原典の規則はもともと side project 向けが前提とされる（出典の注意参照）。

- **不明なら本番扱い。** 「本番判定」で本番でないと根拠を持って言えないリポジトリでは、
  この節を全面適用する。
- **ルール 1 はコード経路だけ。** データ側（ルール 1 の除外リスト）には決して適用しない。
  データの削除・移行・形式変更は、人の明示判断なしに行わない。
- 本番コードでは、互換が要る相手（公開 API、利用中のクライアント、他システム連携）が
  ある場合は互換維持を優先し、その理由を残す。
- ユーザーから「ガードレールを外して」と言われた場合でも、データ側への適用だけは
  外せない。その場合は、コード経路に限って外す旨を確認してから進める。

## 他スキルとの使い分け

- `enhance-readability`（動作維持が前提の作業）が対象の作業では、そちらが優先。
  本スキルは動作変更を伴う実装・レビューでのみ使う。
- `clean-code` と同時に対象になる作業では、責務の分離（clean-code／ルール 4）を優先し、
  本スキルのルール 2 は「将来のための汎用化を足さない」範囲でのみ適用する。
  切り出し先が無いのに新規モジュールを増やす場合は、増やす理由を報告に明記する。

## 使わない場面

- 互換性維持そのものが要件の仕事（公開 API のバージョニング、移行支援、レガシー保守）
- 法令・監査・安全要件で冗長な確認やフォールバックが求められる領域
- 本番データ、DB スキーマ、マイグレーションそのものの作業
- 探索的な調査やスパイクで、捨てる前提のコードを速く書くこと自体が目的のとき
